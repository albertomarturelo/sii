# Wire contract — F29 (Declaración Mensual de IVA)

First-hand observation, no third-party library (ADR-004). All values below are
**synthetic / redacted** — folios, RUTs, montos, names are PII/taxpayer data and MUST
NOT land here. The reads are built in two phases (ADR-013); the filing flow is mapped in
§ Submit (ADR-029).

- **Fase 1 (shipped, robust):** the SDI-**JSON** facades — propuesta + estado.
  **Live-validated from the TS port 2026-06-29** (prod, empresa session): `f29
  formulario`/`overview`/`status` returned real data.
- **Fase 2 (deferred):** the **presented form** via `rfiInternet` **GWT-RPC** — the
  full filed código grid. Mapped in the spike (below); built later (own PR + ADR).

Surface: `@albertomarturelo/sii-core` `portal/f29.ts` (`fetchF29Propuesta`, `fetchF29Estado`) +
`portal/f29-codigos.ts` (the código taxonomy), driven by the `f29Formulario` /
`f29Overview` / `f29Status` tasks under `withSession`.

**SESSION-KEYED (ADR-005).** F29 authorizes by the **session principal**, confirmed
live (Python 2026-06-26): a represented empresa's body RUT → `Consulta RUT no esta
autorizado`. The tasks take NO `--rut` and **reject a representing operate pointer up
front** (before any session) with an actionable "log in as the empresa" message.

## Fase 1 — SDI JSON facades (`propuestaf29ui`)

Base: `https://www4.sii.cl/propuestaf29ui/services/data/facadeAdapterService/`
(host from config `HOSTS.portalApi`). Envelope: the shared SDI shape `{ metaData,
data }`; error channel is **`metaData.errors`** (a list of `{id, descripcion}`) — like
F22, NOT RCV's `respEstado`. `conversationId` = the session `TOKEN` cookie;
`transactionId` = a per-call UUID. Headers: `Referer` = the propuestaf29ui SPA root.

| Facade | Purpose | `data` shape |
| --- | --- | --- |
| `getDeclaracionConCondicionesYTipoPropuesta` | IVA **propuesta** (SII's pre-fill) | object (or `null` = sin propuesta) |
| `getDeclaracionConEstados` | **presented/saved** records (estado) | array (`[]` = nada presentado) |

Namespaces: `cl.sii.sdi.lob.iva.propuestaf29.data.api.interfaces.FacadeAdapterService/<op>`.

**Request bodies** — período split into `mes` (`MM`) + `anno` (`YYYY`); internal form
id `"2"`. SII names the same fields differently per facade (its own quirk, observed):
- propuesta: `{ rutContribuyente, dv, formCodigo:"2", mes, anno }`
- estado: `{ rut, dv, formId:"2", mes, anno }`

**Propuesta response** (`data`, synthetic): `{ tipopropuesta, estado, descripcionEstado,
listCodPropuestos:[{codigo,valor}], listCodAdministrativos:[{codigo,valor}],
listCodBase:[…PII…], resultadoCalculoPP29:{traza:"…RUT…"} }`. `valor` is plain-numeric
(`.`-decimal, no thousands sep) → `Number()`. **PII dropped:** `listCodBase`
(nombre/RUT/dirección) + `traza` (embeds RUT) are never read; NO `raw`. The códigos are
SII's *proposed subset*, served WITHOUT glosas (labeled from the taxonomy below).

**Estado response** (`data[]`, synthetic): `[{ estadoDeclaracionId, estado, folio,
declFechaCreacion, monto, enNegocio, codigo }]`. The `monto` (declared **total a
pagar**) IS surfaced as `total` — the user's own monthly figure, the point of the
overview; it never reaches the audit log. Works for **historical** months. Observed
estados: `1` Vigente, `10` Guardada, `70` "Rechazada por pago inconcluso".

## Código taxonomy (`portal/f29-codigos.ts`)

Observed first-hand from the rendered F29 form HTML (`rfiInternet/cargarHtml`, captured
2026-06-29). The form table gives, per line: **glosa** (`celda-glosa`), **código**
(`celda-codigo`) and **signo** (`celda-signo`: `+`/`-`/`=`). 157 códigos. The `=`
totals delimit the sections used for grouping: `538` TOTAL DÉBITOS, `537` TOTAL
CRÉDITOS, `595` SUBTOTAL IMPUESTO DETERMINADO, `547` Total Determinado, `91` TOTAL A
PAGAR. Groups: `debitos` / `creditos` / `retenciones` / `otros` / `totales`. An
unobserved código → `otros` (surfaced, never hidden — anti-allowlist).

## Fase 2 — presented form via GWT-RPC (`rfiInternet`) — DEFERRED

The filed F29's full código grid (the real balance, incl. computed totals) is NOT in
the SDI JSON. It lives behind `rfiInternet` **GWT-RPC** (`text/x-gwt-rpc`,
pipe-delimited body, `//OK[...]` response). Mapped in the spike, to build later:

- **Warm-up flow:** Mi SII → `www.sii.cl/…1042-3266` → `sifmConsultaInternet` (GWT
  consulta app) → click → `rfiInternet/consulta/index.html` (GWT form viewer). A cold
  cookies-only call bounces to the login wall — the apps must be warmed via this nav
  chain + the `SdiAATokenService.getSdiAAInfoToken` handshake.
- **Key call:** `formularioFacade` op `findDeclaraciones(período)` → response embeds a
  clean `<FormularioRfi><Formulario><ListaCodigos><Codigos tipo="…"><Codigo>/<Valor>`
  XML. `tipo`: `M` = monto (tax line), `C` = text/PII (01 nombre, 06 dirección, 08
  comuna), `N`/`P`/`F` = other. `formularioFacade` op `cargarHtml` → the HTML render.
- **Brittleness:** build-specific strong-name hashes (e.g. the FormularioFacade
  strongName + Java type CRCs) change on every SII redeploy; two GWT apps redeploy
  independently. Hence Fase 2 must drive a real browser (harvest the live serialization
  context / intercept responses), not hand-construct GWT-RPC. Gated on a headless PoC.
- **Revised by the submit capture (2026-10-19, #138).** The form app (`rfiInternet`'s
  `formularioFacade`) replays cold on the cookies-only session when it is entered through
  the propuesta handoff (§ Submit, steps 1–2), with no warm-up nav chain. The redeploy
  brittleness is what ADR-020 already absorbs for SISPAD: layouts derived from the
  permutation, keyed by class name, and a self-healing policy hash. So "must drive a real
  browser" no longer holds for the submit path (ADR-029 amendment). Whether the
  `consulta` viewer's read path above replays cold the same way is still untested.

## Quirks

- `formId` (estado) vs `formCodigo` (propuesta) — same internal id `"2"`.
- `resultadoCalculoPP29.traza` embeds the RUT — never surface it.
- `data:null` propuesta with no `metaData.errors` = "sin propuesta", not an error.
- No reCAPTCHA (the `rb_bf05726fov` POSTs are Dynatrace RUM beacons).
- The GWT-RPC **write** path (`formularioFacade` "Enviar Declaración") is mapped in
  § Submit; its posture is ADR-029.

## Submit — "Enviar Declaración" (ADR-029, spike #138)

Captured live 2026-10-18/19 on the empresa account, período 2026-09: a headed browser
restored from the cookies-only session, with every write blocked, then a browser-free
replay over the HTTP driver up to validation. The owner filed that período from the guarded
browser on 2026-10-18, which captured the two submit calls. No values from those captures
land here.

**Session.** The cookies-only session reaches the whole chain when it is entered through
the propuesta handoff (steps 1–2). There is no warm-up nav chain, unlike Fase 2's read
path, and no Clave re-entry: `SdiFacade.isAutenticationAvailable` is a read. An earlier
"reload bounces to the login" turned out to be the session dying, not the flow (#139).

### The chain

1. **SDI JSON** on `propuestaf29ui` (`facadeService` / `facadeAdapterService`):

   | Op | Request `data` (shape) | Response |
   | --- | --- | --- |
   | `getDeclaracionConCondicionesYTipoPropuesta` | (Fase 1) | the propuesta |
   | `guardarPropuesta` | `{rutCntr, dvCntr, formCodigo:"29", tipoPropuestaInicial:40, periodo:{anno, mes}}` (strings, except the 40) | `data` = a number |
   | `enviarDatosFlujo` | `{rut, dv, periodo:"YYYYMM", form:"29", tipo:40}` | `data` = the rfiInternet entry URL of step 2, plus `tipoFlujo` |

   Both live on `…/propuestaf29ui/services/data/facadeService/<op>`, namespace
   `cl.sii.sdi.lob.iva.propuestaf29.data.api.interfaces.FacadeService/<op>`. The core follows
   the URL `enviarDatosFlujo` answers, and only when it is `rfiInternet` on the portal host.

   `guardarPropuesta` leaves a borrador **"Guardada"** at SII: the flow writes before the
   submit, though nothing is filed. The PPM assistant (`getTasaPPMO`, `getPpmEnPlazo`,
   `getComplementosAsistentes`, and the write `setComplementoAsistentes`) is not on the
   path when the user declares there is nothing to complement.
2. `GET https://www4.sii.cl/rfiInternet?origen=PROPUESTA&accionPpta=PPTA-F29-COMPLETA` (the
   URL step 1 answered) → `302` to `…/rfiInternet/?…`, the form app (HTML, `200`).
3. **GWT reads** on `www4.sii.cl/rfiInternet/formularioFacade` (`requestText`, ADR-020):

   | Op (parameters) | Gives |
   | --- | --- |
   | `consultarHijoToken("PARAM_PROPUESTA")` | a `HashMap<String,String>`: `rut, dv, form, periodo, idBorrador, mostrarAsist, accionPpta` |
   | `getContribuyente(Integer rut, String dv)` | `ResultadoRecuperarContribuyenteTo`; its field 0 is the `SdiContribuyenteTo` |
   | `findAllFormulario()` | `Formulario[]`: the F29 is the one whose field 10 is `"029"` (the other is the F50) |
   | `findPeriodoHabilitado(Formulario)` | `Periodo[]`, each `[Integer año, Integer mes]` |
   | `findVersionBorradorById(Formulario, Periodo, SdiContribuyenteTo, SdiContribuyenteTo, Integer idBorrador)` | `FormularioLayoutTO`: campos, formula metadata, prior values |

   Between `findPeriodoHabilitado` and `findVersionBorradorById` the client sets the
   `Formulario`'s field 0 (`Boolean`) to true and its field 27 (`int`) to 40, and sends that
   same object from then on. The two `SdiContribuyenteTo` are the same object.

   **`idBorrador` is new per flow**: `findVersionBorradorById` with a stale one answers HTTP
   500. The browser also calls `getParametroGlobal`, `SdiAATokenService.getSdiAAInfoToken`,
   `SdiAAService.getSdiAAInfoUsuario`, `getPrecondicionesAlertasPostergacion` (the cód. 756
   notice), `exiteAtributo` (sic), `habilitarAsistentePpm`, `getDecEnTransitoOnload`,
   `getMensajesOnload`, `findCodigosBloqueados`, `getMensajesInf` and `registrarBitacora`
   (its own trail: "VALIDAR FORMULARIO", "ENVIAR SIN PAGO"). None of them feeds a later
   call, and the core does not make them. That SII accepts the chain without them is confirmed
   live by #162.
4. **Fill the form.** Client-side, no call. The propuesta's values already come in the layout;
   the client computes the formula campos and stores them through the widgets it shows (§ The
   form interpreter, below).
5. **Validate.** Right before it, the client stores two flow parameters,
   `crearHijoToken("URL_RETORNO", "-")` and `crearHijoToken("ORIGEN", "PROPUESTA")`; the core
   makes both too. Then `getBorradorRfiValidado(Integer 40, Formulario, Periodo,
   SdiContribuyenteTo ×2, FormularioLayoutTO)` → a large `//OK` whose root is a `BorradorRfi`
   holding two `Borrador`. The browser saves the first. On success the client shows
   "CONFIRMAR DECLARACIÓN SIN PAGO — El Formulario 29 no presenta errores lógicos ni
   matemáticos…" (`sdiFacade getMessage`).

   A `Borrador`'s field 0 is the form rendered as HTML, field 9 the **FormularioRfi XML SII
   would file**, field 27 the tipo and field 28 an integrity value. The XML lists every código
   as `<Codigos tipo="…"><Codigo/><Valor/><Glosa/></Codigos>`:

   | `tipo` | What | The core |
   | --- | --- | --- |
   | `D` | the declared montos (504, 537, 77, 89…) | reads |
   | `R` | the result, 91 TOTAL A PAGAR DENTRO DEL PLAZO | reads |
   | `E` | the header: nombre, RUT, dirección, comuna, período, folio | never reads |
   | `N` | SII-internal (versión, unidad operativa, traza IP…) | never reads |
6. **Submit, two calls:**
   1. `guardarBorradorRfiValidado(Borrador)` with the validated `Borrador` and its field 27
      (a `java.lang.Integer`, tipo) 40 → 41; everything else unchanged, including the integrity
      value at index 28. **It saves; it does not file.** Response: a `Borrador`.
   2. **`inyectarBorradorRfi(Borrador)`**, with the `Borrador` from call 1, unchanged.
      **This files.** Response `//OK[1,1,["java.lang.Boolean/…"],0,7]` (true).

   The client then calls `crearHijoToken` and lands on `propuestaf29ui/#/declarecibida`
   ("Tu Declaración de F29 ha sido recibida con éxito").
7. The folio and estado come from Fase 1's `getDeclaracionConEstados`; the PDFs from
   `f29-pdf.md` (live-validated right after this filing over the HTTP driver).

### SII's validation is not a safety net

Step 5 on the layout **as `findVersionBorradorById` returns it** (step 4 skipped) answered
`//OK` and "no presenta errores". The borrador lacked 77 (remanente para el período
siguiente) and 537 (total créditos), and still carried 543 / 547 / 573 / 598 / 755 / 774
from an earlier draft. SII's validation neither recomputes nor flags omissions; ADR-029's
safety rule exists for this.

**The rule, as built (#161).** `verificarBorradorF29` compares the `D`/`R` códigos of the
validated XML (non-zero) with what the propuesta and the formulas imply: every non-zero
propuesta código, and every formula campo the interpreter left non-zero. A código can be
`falta` (expected, not declared), `distinto` (declared with another value), `sobra` (declared,
expected by nothing: a stale value) or `formula_vs_propuesta`. Any entry refuses the submit
before `guardarBorradorRfiValidado`; the message names códigos, never amounts. Checked locally:
run5 and run6 give no entry, and the experiment's validation of the unfilled layout gives
`77 falta` and `537 falta`. A formula campo that never reaches the XML would show as `falta`
and refuse a valid filing; the months #179 exercises tell whether one exists.

### The GWT-RPC codec (protocol 7, #159)

rfiInternet speaks GWT-RPC **protocol 7** (SISPAD, ADR-020, speaks 5). The core's codec is
`portal/gwt.ts` (`Gwt7Codec`), the transport `portal/f29-rfi.ts` (`callFormularioFacade`).

- **Request:** `7|0|N|<N strings>|<payload>|`, forward. Strings are escaped as the client does:
  `\0`, `\!` (pipe), `\\` and `\uXXXX` for a set of Unicode ranges.
- **Response:** `//OK[<payload, backwards>, [strings], 0, 7]` as a JS literal. Large ones are
  split as `"…"+"…"` and `[…].concat([…])`.
- **Leaves:** booleans travel as `1`/`0`, ints and shorts as integers, a long as GWT's base64
  token.
- **Four rules found by checking every captured call:**
  - a `java.lang.String` parameter is a bare string ref, not an object;
  - a `String` or primitive return value is bare too (`//OK[1,["…"],0,7]`), and `void` is
    `//OK[[],0,7]`;
  - a `String[]`'s elements are bare string refs;
  - equal boxes the client's JRE caches are ONE object, written once and then back-referenced:
    every `Boolean`, and `Byte` / `Short` / `Integer` / `Character` in -128..127 (0..127 for
    `Character`), because `valueOf` and the deserializers share them. Rebuilding a request from
    decoded responses has to reproduce that (#161: the `Formulario`'s flags share one
    `Boolean`, and it shares an `Integer` with the contribuyente).
- **Policy and signatures, at runtime.** Each service proxy is
  `Yc.call(this, <base>(), '<entryPoint>', '<policy>', …)` in the permutation, and each type
  signature a `<var>='<class>/<crc>'` constant. The core reads both from the live permutation
  (`rfi.nocache.js` → `<strong-name>.cache.html`), caches them, and re-reads once if SII refuses
  the policy (`IncompatibleRemoteServiceException`). If the refusal persists, the call fails as
  "scraper roto": the layouts are stale, not the deploy. No CRC is a constant in the code.
- **Field layouts, generated.** `portal/rfi-schema.ts` (152 writable, 257 readable classes) is
  derived from permutation **`543D42AD0EF9E262804F560CE81AF5A6`**, observed **2026-10-19**, by
  `docs/sii-contract/rfi-schema-extract.py`. Two layouts are asymmetric in SII's compiled code
  itself: `DateRecord` writes a trailing long it does not read, and `SdiSimpleDateTo` reads
  nothing.
- **Verified against the captures.** Every captured request (140) re-encodes byte for byte, and
  every response (127) decodes with its declared return type. The `Borrador` that
  `guardarBorradorRfiValidado` returned re-encodes into exactly the `inyectarBorradorRfi` request
  that filed 2026-09. That check runs locally only (`SII_F29_CAPTURES`,
  `portal/gwt-captures.test.ts`), since the captures carry the empresa's data.

### The form interpreter (#160)

`portal/f29-rfi-form.ts` (`fillF29Form`) does step 4 the way the client does. Everything was
read from the client's compiled code in permutation `543D42AD0EF9E262804F560CE81AF5A6`
(observed 2026-10-19); the formulas themselves are SII's data, not code of ours.

- **What the layout holds.** The `Formulario` instance carries:
  - every campo by key (`cod813`, `varP94`…), each with its `CampoMetadata`: código, formula,
    type, maximum length and decimals;
  - the formula ASTs (3551 `Expresion`), and 235 `Regla` in its metadata;
  - 112 parameter tables (`mapaParametros`…).
- **The evaluator** is the client fn `PG`. The F29 uses 27 operators: arithmetic,
  comparisons, `AND`/`OR`/`->`/`NOT`, `?:`, `EXISTE_DATO`, `ISNULO`, `PSTV`/`ABS`/`NEG`, `ROUND`,
  `MINL`/`MAXL`, `GET_VALUE`, `PROX_PERIODO`/`AANT_PERIODO`. A reference is `$cod<N>`, and the
  node's type (`f`, 64 + data type) says how to compare.
- **SII's decimal class, not IEEE or Java's.** A result always prints one decimal (`"5.0"`), a
  division keeps 2 decimals, rounding is half-up on the magnitude, and a product can yield
  `-0.0`. `ROUND` rounds the fraction alone with `Math.round`, so `-12.5` becomes `-11`. Kept
  as observed.
- **How a value is stored.** A campo with a formula always READS as its result (`rC`), but the
  serializer sends the STORED value. The client stores a result only through the widget that
  shows the campo: a `TEXTBOX` (`jL`) or `CHECKBOX` (`GK`/`QL`) refresh. On that refresh a
  numeric zero is stored as `''`, unless the metadata's `B` is `"0"`. So:
  - formula campos no cell shows keep what the layout brought;
  - a shown campo whose formula is now zero goes empty. That is why the stale 543 / 547 / 573 /
    598 / 755 / 774 disappear.
- **The propuesta screen (`QRb`, mode `PPTA-F29-COMPLETA`)** sets the 773 and 778 checkboxes
  (postergación de IVA) to `FALSE` when the layout shows them.
- **A read-only `TEXTBOX` cell** is built as a hidden-value field (`wM`): visible `FALSE`, CSS
  class `fw-campoOculto`, and width `125px` when it had none.
- **Rules (`GC`).** A rule with no group or the `DEFAULT` group fails when its expression is not
  `TRUE`; kind 1 is ignored. SII's message is surfaced verbatim. That the validation calls `GC`
  with no group is an assumption, consistent with run6 (no rule fails). The submit stops on any
  failing rule before it validates, with SII's messages.
- **The codec detail this exposed.** In the client a JS string is its value, so two `String`
  objects with the same text are written once and then back-referenced. `Gwt7Codec` does the
  same.
- **Verified against the captures, locally** (`f29-rfi-form-captures.test.ts`,
  `SII_F29_CAPTURES`). Filling the layout `findVersionBorradorById` returned gives:
  - exactly the 10 campos the browser changed: 77, 537, 543, 547, 573, 598, 755, 773, 774 and
    778;
  - no failing rule;
  - a `getBorradorRfiValidado` request byte for byte identical to the browser's (356,515
    bytes), on both run5 and run6.

  An unknown operator, widget, type or a multivalued section is "scraper roto", never a silent
  0. What the 2026-09 shape does not exercise (PPM, retenciones, débito > crédito) is #179's
  synthetic oracle.

### Errors

When a call fails, the client stores `crearHijoToken("PARAM_RFI","ERR-2")` and bounces to the
propuesta with "Se ha producido un error al realizar la transacción." plus a code:

| Code | Failed step |
| --- | --- |
| `[mod-gdrpro-rfi3]` | `guardarPropuesta` |
| `[mod-envdf-rfi3]` | `enviarDatosFlujo` |
| `[]` | an rfiInternet validation / submit call |

The client also retries `crearHijoToken` in a tight loop when a precondition read fails. We
never do (ADR-004).

Only SII's own exception (`//EX`) proves an rfiInternet call took no effect; the core raises it
as `F29RechazoError`. Any other failure of `inyectarBorradorRfi` (a lost answer, a body that does
not decode, a dead session) leaves the filing's outcome unknown: the submit reads the estado,
reports a `Vigente` declaración as filed, and otherwise says it could not confirm and must not
be resent.
